# Issue Graph — аудит юзабилити / производительности / визуала

Дата: 2026-06-07. Метод: многоагентный разбор по 5 направлениям (perf, раскладка,
UX, паритет с GitLab, инструменты холста) + независимая ревизия. Все находки
верифицированы по коду (`file:line`).

Связанный документ: [ROADMAP.md](./ROADMAP.md) — план работ по этапам.

---

## TL;DR — две разные болезни, которые складываются

Жалобы пользователя «долго грузит» и «нечитаемая полоса» — это **два независимых
бага**, и починка одного **не лечит** второй:

- **A. Медленно** — N+1 запросов к GitLab при сборке графа (`graph.py`).
- **B. Нечитаемо** — вырождение dagre-раскладки на несвязанных нодах + `fitView`
  с `minZoom=0.1` (`layout.ts`, `App.tsx`).

> Если ускорить только бэкенд — получим ту же нечитаемую полосу, просто быстрее.
> Если починить только раскладку — читаемый граф будет грузиться 10–60 c.
> «Юзабельно» = **оба класса правок**. Начинать — с раскладки/вида: дёшево,
> мгновенно, без зависимости от бэкенда.

Severity-сводка: **3 critical**, **9 high**, **10 medium**, **8 low**.

## 1. Производительность (скорость загрузки)

| # | Находка | Severity | Где | Почему больно |
|---|---------|----------|-----|---------------|
| P1 | **N+1 по связям**: отдельный `GET /projects/{pid}/issues/{iid}/links` на каждую задачу | 🔴 critical | `graph.py:88-110` `_collect_links`; семафор `concurrency=12` `gitlab_client.py:57`, `config.py:38` | N сетевых round-trip. N=300 → ~300 запросов пачками по 12; при RTT 50–150 мс это ≥2.5 c только на связи. Доминанта времени холодной загрузки |
| P2 | **Вложенный N+1 по эпикам, последовательно** (без `gather`) | 🟠 high | `graph.py:122-140` `_collect_epics`: `for ep in epics: await paginate(.../issues)` | E эпиков = E последовательных пагинаций друг за другом. 50 эпиков ≈ +5 c сериями. Худший паттерн параллелизма в проекте |
| P3 | **Дефолтный scope = вся группа** (`graphlab`/первая) → все задачи всех подпроектов, `state=all` | 🟠 high | `App.tsx:219-222`; `graph.py:61-64` (`scope=all&state=all`) | Первый заход сразу попадает в worst-case запрос, который пользователь не просил |
| P4 | **Полный пересчёт dagre на каждый символ поиска** (нет дебаунса) | 🟠 high | `App.tsx:303-327` `visibleIds`(deps: `search`) → `App.tsx:437-470` `positioned` → `dagreLayout`; `App.tsx:945` `setSearch` без debounce | На сотнях нод каждый символ перезапускает O(V+E) раскладку + пересоздание RF-нод → фризы при печати |
| P5 | **Скрытый wasted-recompute в режиме `dim`**: вход dagre не меняется, но `visibleIds` в deps → пересчёт всё равно | 🟠 high | `App.tsx:470` — `visibleIds` в массиве зависимостей `positioned` | Чистая потеря: dagre гоняется без изменения входа. Бесплатный фикс — убрать зависимость |
| P6 | **Кэш per-session in-memory, TTL=60 c, без прогрева/SWR** | 🟡 medium | `main.py:456-481`, `main.py:70/187-189`; `config.py:39`; `api.ts:23-24` | Каждые 60 c, каждый новый браузер и после рестарта uvicorn — полный N+1 синхронно под спиннером |
| P7 | **`paginate` последовательный** (страница за страницей) | 🟡 medium | `gitlab_client.py:105-123` | На тысячах задач/меток страницы не параллелятся. Бьёт по issues, по 4 paginate в `/api/scope-meta`, по `/api/namespaces` |
| P8 | **Эффект dimming проходит по всем нодам/рёбрам на каждое выделение/фильтр** | 🟢 low | `App.tsx:496-534` (`setNodes(map)`, `setEdges(map)`) | Доп. O(V+E) и полный ререндер RF при каждом изменении выделения/поиска |
| P9 | **Нет виртуализации/LOD в ReactFlow** | 🟢 low | `App.tsx:1071-1104` (нет `onlyRenderVisibleElements`); `IssueNode.tsx:24-112` рисует полную карточку при любом зуме | На сотнях нод DOM/SVG тяжелеет; при `minZoom=0.1` рисуются все детальные карточки, которые нечитаемы |

**Worst-case оценка (N=300, 20 проектов, холодный кэш):** 1 paginate issues +
~300 `/links` + (PRO) E последовательных пагинаций эпиков + 4 paginate
scope-meta → ~330+ HTTP-запросов. GraphQL свёл бы это к ~3–6.

Цель пользователя: **практически не переходить в GitLab**. Сейчас Sidebar
показывает только поля из ноды графа (`_issue_to_node`). Отдельного запроса
деталей задачи **нет вообще** — поэтому самое ценное недоступно.

## Пробелы, которые заметила только ревизия (важно)

1. **Порядок perf vs раскладка.** Ни один game-changer по отдельности не делает
   продукт юзабельным (быстро-но-нечитаемо **или** читаемо-но-медленно).
   Первой чинить — раскладку/вид (дёшево, без бэка).
2. **Wasted-recompute в `dim`-режиме** (P5) — отдельный бесплатный фикс.
3. **Инвалидация кэша при мутациях** не разобрана: после SWR риск показать
   устаревший граф после своей же правки → нужна точечная инвалидация ключа scope.
4. **Общий кэш по `(url|scope)` ломает права**: у разных OAuth-токенов разная
   видимость (confidential/приватные проекты). SWR — только в пределах сессии,
   не глобально.
5. **Маппинг рёбер при GraphQL — риск ДАННЫХ, не «просто маппинг».** `_dedupe_edges`
   (`graph.py:149-176`) накладывает store-оверлей `blocks/parent` поверх
   симметричного `relates_to`. GraphQL `linkType` и порядок src/tgt отличаются —
   при ошибке сломается направление стрелок и пользовательские оверлеи. Нужен
   общий маппер + тест паритета REST vs GraphQL до выкатки.
6. **Фикс раскладки может ухудшить рендер**: раскладка по всем нодам + `hidden`
   вместо выкидывания → растёт число DOM-нод. Включать `onlyRenderVisibleElements`
   **одновременно**.
7. **Нет измеримых критериев приёмки** (см. ROADMAP).
8. **Нет тестов под GraphQL/фолбэк** (в репо есть практика тестов без тяжёлых
   зависимостей).

## Вердикт

Продукт доводится до юзабельного состояния. Минимум — **не один большой
рефактор**, а связка: (1) дешёвые правки восприятия сегодня; (2)
`connectedComponentsLayout` + `onlyRenderVisibleElements`; (3) развязка раскладки
от поиска. Этого хватает для читаемости и отзывчивости на реальных данных.
GraphQL обязателен для группового scope с сотнями задач, но его можно отложить за
быстрые победы, если сначала сузить дефолтный запрос (`state=opened`) и/или
стартовать с «Моих задач».
